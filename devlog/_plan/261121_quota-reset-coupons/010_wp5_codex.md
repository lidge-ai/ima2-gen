## 0. Safety and identity model (revised after audit round 2: R2-F1..F8)

Identity (R2-F1, R2-F4):
- Ledger key = stable physical identity, never a credential fingerprint. Codex: `codex:<accountId>` (CodexSessionStore already rejects a session without accountId, session.ts:64-69; quota reads without it fail closed). Grok: `grok:oidc:<sub>` per 020 §1 (none → coupons unavailable).
- No credential-generation hash. Refresh-token rotation is normal (session.ts:4-9,122-149) and must not split the ledger. The account check that matters is "the account that will be charged is the account the user confirmed": accountId/userId captured at confirmation and compared immediately before dispatch and before publishing the result. A→B→A between confirm and dispatch charges A, which is what the user confirmed; switching to B fails with IDENTITY_CHANGED. Credential rotation or a candidate moving to another source path keeps the same key, so unresolved operations stay visible and blocking.
- Grok identity: see 020 §1 (server-asserted identity of the exact bearer from the ima2 xAI session; the ~/.grok CLI credential is never used for coupons).

Ledger states and fencing (R2-F3):
- `claimed` (row inserted, nothing sent) → `sending` (compare-and-set `WHERE operation_id=? AND state='claimed' AND owner=?` executed immediately before the network write; if it changes 0 rows the owner aborts without sending) → `settled` | `unknown`.
- Owner liveness = heartbeat row (`reset_owners(owner_id, pid, heartbeat_at)`) refreshed every 5 s by each server process. Recovery may act only when the owner's heartbeat is older than 60 s: a stale `claimed` becomes `abandoned` (provably not sent, because the CAS to `sending` can no longer succeed: recovery flips state first), a stale `sending` becomes `unknown`.
- `unknown` can be acknowledged by the user (acknowledged_at, acknowledged_by principal, note). Acknowledging means "the earlier attempt may have consumed one credit"; a later redeem is a new, separately confirmed intent. A paused owner that resumes after its `sending` was marked unknown can only complete that same single send (its CAS already happened), so one operation never sends twice.
- Unresolved = `claimed|sending|unknown`; partial unique index on (provider, ledger_key) WHERE state IN those values.

Auto-redeem target reservation (R2-F2):
- NEW table `reset_targets(provider, ledger_key, target_key, operation_id, created_at, PRIMARY KEY(provider, ledger_key, target_key))` where target_key = `granted_at|expires_at`. Auto-redeem inserts the reservation in the same transaction as its claim; the row is kept after settlement, so a second scheduler that inspected the same credit fails the insert even when the first already settled. Manual Codex redeem does not name a credit (WHAM consume has no credit id), so it reserves nothing; it is still serialized with auto-redeem by the account-wide unresolved index. Manual-after-auto-settled is a new user intent and is allowed.

Consumption guard (R2-F5):
- All consuming wire calls go through `lib/reset/transport.ts`; it refuses (throws CONSUME_DISABLED) whenever `process.env.IMA2_RESET_DISPATCH_DISABLED === "1"`. `scripts/run-tests.mjs` sets that variable for the whole test process tree (children inherit env), and the screenshot fixture server sets it too. A test asserts the guard (env set → transport throws before any socket), and a source test asserts the consume URLs appear only in lib/reset/transport.ts. Tests additionally inject fake transports; fake consume invocations are counted separately from the guard's refusal counter.
- Failing-first seams: commit 2 adds the new modules as typed seams whose functions throw `Error("not implemented")` so each test file loads and each test fails on its own call/assertion; commit 3 replaces every seam (a test asserts no "not implemented" remains under lib/reset and lib/quota).

Confirmation principal (R2-F6):
- `lib/localLanAccess.ts` guard sets `res.locals.accessPrincipal = { mode: "loopback" | "lan-cookie" | "lan-token", principalId }` (non-secret: sha256 prefix of the LAN session id or token; "loopback" constant for local mode). Confirmation tokens bind to that principal; redeem from another principal → 403. Tests: cross-session use, revoked LAN session, concurrent use of one token (exactly one admitted).

Auto-redeem runtime control (R2-F7): the settings route calls `autoRedeem.reconfigure(config)` in-process on enable/disable/lead change (start, stop, reschedule); every scheduler also re-reads the persisted config each 60 s tick so another server process converges; tests cover enable-after-start, disable-while-scheduled, lead change reschedule.

Durations (R2-F8): exactly 18000 s → "5h", 604800 s → "7d", 2592000 s → "30d"; every other positive duration is rendered from seconds (e.g. "29d", "90m"); nonpositive/non-finite → label null.

Round-3 revisions (R3-F1..F6), superseding the matching §0 text above:

- R3-F1 (post-CAS pause): `unknown` has two origins. `unknown/owner` is written by the owner itself after its single send settled or aborted (the code path has returned, so no later send exists); it can be acknowledged. `unknown/recovered` is written by recovery for a stale `sending` row; it can be acknowledged only when `process.kill(owner_pid, 0)` reports the owner process gone (ESRCH). If the pid exists (paused owner, or pid reuse), acknowledgement is refused with "restart ima2 / end the stuck process first"; pid reuse only makes the rule more conservative. Until acknowledged, the row keeps blocking the account. Tests: pause after CAS (fake transport awaiting a gate), recovery → unknown/recovered, acknowledge refused while the owner pid is alive (the test process itself), allowed after owner exit (child process owner killed), and a new redeem only after acknowledgement.
- R3-F2 (manual vs auto): table `reset_accounts(provider, ledger_key, revision INTEGER)`; every claim (manual or auto) increments `revision` in its claim transaction. Auto-redeem records the revision before inspection and claims with `UPDATE reset_accounts SET revision=revision+1 WHERE … AND revision=?`; 0 rows ⇒ re-inspect and re-plan. Grok manual redeem names a tokenId, so it also inserts a `reset_targets` row (same coupon cannot be redeemed twice). Test: auto inspects → manual claims+settles → auto claim fails on revision → fresh inspection.
- R3-F3 (disable across processes): auto-redeem settings live in the db (`reset_settings(provider, enabled, lead_minutes, updated_at)`), not config.json. The settings route updates that row in a transaction; the auto claim transaction re-reads it and aborts when disabled, and the owner re-reads it again in the same transaction as the CAS to `sending`. SQLite serializes those transactions, so a disable committed before the CAS always wins. The 60 s tick remains only for rescheduling. Test with two connections: disable on A between B's inspection and B's CAS ⇒ no send.
- R3-F4 (guard at every entry point): the dispatcher (`lib/reset/dispatch.ts`), not the transport, enforces the prohibition: while `IMA2_RESET_DISPATCH_DISABLED=1` it calls only transports carrying the private `FAKE_TRANSPORT` symbol from `tests/helpers/fakeResetTransport.ts` and throws before any other transport is called. Every reset test file starts with `import "./helpers/resetTestGuard.ts"` which sets the flag (so direct `node --test <file>` is covered) and installs a socket sentinel (wraps `net.Socket.prototype.connect` and `tls.connect`; non-loopback connect throws and is counted). `scripts/run-tests.mjs` and the screenshot fixture also set the flag for child processes. Tests: real transport under the flag throws before the sentinel sees a connection; fake dispatches are counted separately; the sentinel count is 0 at the end of every reset test file.
- R3-F5 (behavioral failing-first): commit 2 ships naive baseline implementations, not throwing seams: ledger without unique/CAS/recovery, dispatcher without identity re-check or settings re-read, window classifier = current positional rule, credits projection = current (drops fields), auto-redeem reading enabled once at start. Each safety test therefore runs and fails on its behavioral assertion; commit 3 replaces the baselines. 011 records per-test baseline failures and the post-implementation passes.
- R3-F6: superseded by 020 §1 (round 5).
- R4-F1: a transition to `abandoned` (stale `claimed`, or a pre-send abort) deletes that operation's `reset_targets` row in the same transaction; `sending`, `unknown` and `settled` keep it. Test: crash after claim before CAS for Codex auto and Grok manual → after recovery the same credit/coupon can be attempted again.
- R4-F2: every server process starts the auto-redeem watcher at boot regardless of the setting; while disabled it only re-reads `reset_settings` every 60 s (no inspection, no network). When the pre-send settings check inside the CAS transaction finds the feature disabled, the row goes `claimed → abandoned` (and its reservation is released) in that transaction. Tests: two servers boot disabled, enable via A, stop A, B starts scheduling within one tick; disable between claim and CAS → abandoned + reservation released, no send.
